# Request for pfit-claude Reference Material

Please inspect the `pfit-claude` repository and produce a compact reference packet for porting its behavior to the local Ollama-based `pfit` workflow.

The goal is not to copy implementation wholesale. The goal is to preserve the same user-facing workflow and core capabilities while keeping the local implementation minimal, YAML-based, and easy to explain.

## Needed Artifacts

1. End-to-end workflow contract
   - Exact behavior of `pfit new`, `pfit check`, `pfit jax`, `pfit run`, and `pfit diagnose`.
   - Required inputs and generated outputs for each step.
   - Which files each step reads and writes.
   - Any repair loops, retry behavior, validation gates, or user confirmation points.

2. YAML/session schema
   - The expected session directory layout.
   - Required and optional YAML fields.
   - How states, parameters, fixed parameters, initial conditions, observables, derived outputs, datasets, losses, and optimizer settings are represented.
   - Any examples of valid minimal and advanced session specs.

3. JAX translation contract
   - What `pfit jax` expects the model to generate.
   - The smallest valid JAX fragment/API surface needed by the framework.
   - How Python/NumPy user model code should map to JAX, including:
     - `numpy` to `jax.numpy`
     - indexed assignment to `.at[...]`
     - loops over data or states
     - conditionals
     - helper functions
     - fixed parameters
     - derived observables/writeout values
     - custom loss functions

4. Runtime API mapping
   - Which parts of JAX, Diffrax, Optax, Equinox, or other libraries the generated code is allowed to use.
   - Which parts are owned by the framework and should not be generated by the model.
   - Preferred replacements for common Python/SciPy/NumPy idioms.

5. Optimizer and loss behavior
   - How pfit-claude chooses optimizers, losses, transforms, parameter bounds, or schedules.
   - Which choices are made by the LLM versus deterministic framework code.
   - Minimal examples showing custom loss definitions and derived-observable fitting.

6. Representative examples
   - A small simple ODE example.
   - A model with unobserved states.
   - A model with derived observables.
   - A model with fixed parameters.
   - A model with helper functions.
   - The Boehm/STAT5 and Oregonator examples.

For each example, please include:
   - input user prompt or source files
   - resulting YAML/session files
   - generated user model
   - generated JAX output
   - any expected diagnostics or warnings

7. Error and validation behavior
   - Common failure modes detected by pfit-claude.
   - How malformed model output is repaired.
   - Which errors are fatal versus warnings.
   - Any deterministic validation that runs after an LLM step.

## Preferred Format

Please return this as concise Markdown with code snippets only where they clarify a contract. Avoid long implementation dumps unless a function defines a public API the local implementation must match.

Most important: identify the boundary between what the LLM is responsible for and what the deterministic framework is responsible for.
